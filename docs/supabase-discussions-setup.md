# Обговорення книг і коментарі — міграція 012

Після застосованих 001–011 підготовлено `202611120012_club_discussions.sql`.
За підтвердженням власниці проєкту, міграцію 012 застосовано вручну до розробницького
Supabase. Перевірено створення й редагування тем, коментарі, модерацію, soft delete,
архівний режим, відновлення клубу та F5. SQL-тести безпеки й конкурентності ще не виконані.
Чинні notifications, генератор і Cron не змінюються.

## Дані та доступ

`club_discussions` — тема клубу з необов’язковим посиланням на книгу будь-якого статусу.
Складений FK `(book_id,club_id)` використовує унікальність із 006 та забороняє чужу книгу.
`club_discussion_comments` — плоский список, без відповідей на коментарі.
Тексти звичайні, з переносами рядків. Перевірки довжин є в React та БД.

Таблиці мають RLS без клієнтських політик і без SELECT/INSERT/UPDATE/DELETE-грантів.
Усі дані повертаються явними RPC-проєкціями; загальні права profiles не розширюються.
Приватні SECURITY DEFINER реалізації з порожнім search_path перевіряють активність
акаунта та актуальні права; публічні SECURITY INVOKER обгортки відкриті лише authenticated.
Внутрішні helper-функції закриті. author_id і час визначає сервер.

Власник, чинний учасник та admin можуть читати. Заявник і сторонній — ні.
Писати може власник/чинний учасник активного клубу; admin без членства лише модерує.
Автор редагує лише свої записи. Власник/admin видаляє чужі, але не переписує їх.
Після виходу/виключення звичайний користувач втрачає читання і запис, його внесок залишається.
Архів повністю незмінний, включно з модерацією. Після restore знову діють поточні права.

## Видалення та конкурентність

Soft delete з очищенням: title/body теми або body коментаря стають NULL;
CHECK дозволяє це лише разом із deleted_at/deleted_by. Відновлення не передбачене.
Видалена тема не входить до списку; деталі повертають лише заглушку й службові прапорці.
Її коментарі не читаються й не змінюються. Збережений текст інших коментарів не копіюється
до відповіді видаленої теми. Видалений коментар залишається заглушкою без тексту та імені.

Порядок блокувань: user_access → clubs → topic → comment. Доступ і archived_at
перевіряються після блокування клубу. Зміни членства використовують той самий клубний lock.
Оновлення/видалення вимагають точного очікуваного updated_at; конфлікт — SQLSTATE 40001.
Тригер забезпечує монотонний updated_at з мікросекундами; JavaScript не перетворює
версію на Date. При конфлікті текст форми лишається до явного перечитування даних.
Підтвердження видалення утримує початкову версію запису: фонове перечитування або
перехід сторінки коментарів не підміняє версію вже підтверджуваної теми.
Списки повторно перевіряють доступ у тому самому SQL statement, що вибирає дані;
коментарі додатково приєднані до невидаленої доступної теми. Після паралельної зміни
доступу/видалення між попередньою перевіркою та вибіркою текст гілки не повертається.
Звичайне MVCC-читання не відкликає вже отримані дані або snapshot читання, що передував зміні.
Нормалізація Unicode-пробілів узгоджена з JavaScript trim(); серверні CHECK використовують
ту саму закриту функцію нормалізації, включно з NBSP та вертикальною табуляцією.

## Інтерфейс

Маршрути `/clubs/:clubId/discussions`, `/new`, `/:discussionId`, `/:discussionId/edit`.
Локальне завантаження без нового глобального провайдера; скасування читань і remount за акаунтом.
Теми: created_at DESC,id DESC; коментарі: created_at ASC,id ASC. Сторінки по 20.
Фільтр книги та сторінка тем у URL, сторінка коментарів — `comments`.
Кількість коментарів у списку рахує лише невидалені записи; пагінація коментарів включає заглушки.
Підтвердження видалення, Escape, повернення фокуса, блокування повторних надсилань.

## Фінальний план SQL-перевірок в одноразовому середовищі

1. У чистому одноразовому Supabase застосувати 001–012 у порядку імен. Реальну БД не очищати.
2. Виконати `club_discussions.test.sql` і попередні SQL-набори; SQL-тести ще НЕ виконані.
3. `club_discussions_concurrency.spec` — для isolationtester, не SQL Editor і не pgTAP.
   Перевірити двох авторських клієнтів зі старою версією, видалення/архівування/виключення
   одночасно зі створенням коментаря. Очікуються конфлікт або відмова, а не deadlock чи запис після втрати прав.
   Додаткові перестановки перевіряють редагування проти видалення теми/коментаря,
   зворотний порядок коментар → видалення теми та читання після втрати членства.
4. JWT-перевірки власника, учасника, admin без членства, заявника, гостя і заблокованого.
5. Перевірити F5, зміну акаунта, вузький екран, клавіатуру та збереження введення при помилках.
6. Перевірити відсутність старого тексту після видалення в БД і RPC та незмінність попередніх модулів.

Додаткові розширення, Storage, налаштування Cron або нові бібліотеки не потрібні.
Повний SQL-прогін запланований на фінальний етап курсової. React-тести не замінюють SQL-перевірки.
