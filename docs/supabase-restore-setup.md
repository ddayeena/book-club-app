# Відновлення клубів — міграція 010

Підготовлено `202611120010_restore_club.sql` після 001–009.
Міграція не застосована автоматично. Нових таблиць, політик RLS, розширень,
нагадувань, Cron або змін попередніх міграцій немає.

## Права й наслідки

- public.restore_club(p_id uuid): SECURITY INVOKER, тільки authenticated.
- private.restore_club: SECURITY DEFINER, search_path='', перевірки через наявні
  require_actor() → manages_club(uuid) → lock_club(uuid,true) → повторний manages_club(uuid).
- require_actor повертає uuid і блокує активний рядок user_access FOR SHARE.
  lock_club повертає public.clubs і блокує клуб FOR UPDATE. Внутрішні helpers
  не отримують нових EXECUTE-привілеїв; private.restore_club доступна authenticated
  для роботи публічної invoker-обгортки. Кожен виклик усе одно перевіряє права.
- Активний власник відновлює свій клуб; активний адміністратор — будь-який.
  Учасник, сторонній, заявник, гість або заблокований користувач не можуть відновлювати.
- UPDATE змінює archived_at на NULL; чинний touch-тригер оновлює updated_at.
  У вже активному клубі повторний виклик не виконує UPDATE.
- Заявки, членства, книги, голоси, голосування, зустрічі та повідомлення не змінюються.
  Раніше відхилені заявки залишаються відхиленими. Майбутні скасовані зустрічі
  та скасовані/зафіксовані голосування не відкриваються повторно.
- Тригер archive_meetings реагує лише на NULL → archived_at, тому зворотна
  зміна не змінює зустрічей. Історична дата next_meeting також залишається.
- Відновлений клуб знову видимий у каталозі; керування його модулями працює
  за чинними правами. Блокування власника не забороняє активному адміністратору
  відновити клуб, але не знімає блокування з акаунта власника.

## React

На сторінці архівного клубу кнопка доступна власнику/адміністратору.
В адмінпанелі — у наявному блоці адміністративних дій.
Підтвердження пояснює публікацію клубу та незмінність скасованих подій.

Клієнт не змінює archivedAt оптимістично. Після RPC перечитує каталог/адміністративні
деталі. «Мої клуби» використовує оновлені дані того самого ClubsProvider.
Помилка RPC залишає попередній стан, повідомлення показується користувачу.
Повторні натискання блокуються; Escape скасовує підтвердження й повертає фокус.
Після успіху фокус переходить до повідомлення або заголовка деталей.
При помилці повторного читання слід оновити дані: успішний RPC уже міг відновити клуб.
Повідомлення каталогу явно розрізняє успішне відновлення та помилку перечитування;
кнопка повторного завантаження повторює читання без повторного RPC відновлення.
Повторний запит безпечний.

## Окремий ручний сценарій конкурентності

Це сценарій для двох незалежних SQL-сесій тестової БД; він не запускався локально.
Використовуйте заздалегідь створений тестовий клуб, його активного власника й активного
адміністратора. Підставте реальні UUID тестових fixtures.

У кожній сесії:
```sql
begin;
set local role authenticated;
select set_config('request.jwt.claims',
  '{"sub":"<actor-uuid>","role":"authenticated"}',true);
```

A. Архівування → відновлення:
1. Сесія A (власник): викликати archive_club('<club-uuid>'), не виконувати COMMIT.
2. Сесія B (адміністратор): викликати restore_club('<club-uuid>').
   Запит має чекати блокування клубу.
3. Сесія A: COMMIT. Сесія B завершує RPC, потім COMMIT.
4. Перевірити: клуб активний; події, скасовані архівуванням, залишаються скасованими.

B. Відновлення → архівування:
1. Початковий стан клубу — архівний.
2. Сесія A: restore_club, утримати транзакцію.
3. Сесія B: archive_club — чекає блокування.
4. COMMIT A, потім COMMIT B. Клуб має бути архівним.

C. Два відновлення:
1. Обидві сесії викликають restore_club для одного архівного клубу.
2. Другий запит чекає першого; після COMMIT першого завершується без зайвого UPDATE.
3. Жодні дочірні записи не змінені. Зафіксувати updated_at після першого commit
   й переконатися, що повторне відновлення його не змінює.

Результат визначається порядком отримання блокування, а не часом натискання кнопок.
Застарілий інтерфейс потрібно перечитувати. Тести з одним з'єднанням не доводять
відсутність усіх можливих deadlock; паралельні сценарії перевіряються окремо.
