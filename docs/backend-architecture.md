# Backend-архітектура ReadHub

ReadHub використовує Supabase Auth, PostgreSQL і Storage. React звертається до них через сервісний шар: Auth керує сесією, PostgREST/RPC — предметними даними, Storage API — аватарами. Визначення backend зберігаються в незмінних [міграціях 001–012](../supabase/migrations/).

Це опис завершеної архітектури. Практичне налаштування нового середовища наведено окремо в [supabase-setup.md](supabase-setup.md), frontend — у [component-architecture.md](component-architecture.md), фактичні результати перевірок — у [verification.md](verification.md).

## Auth, профілі та ролі

Supabase Auth забезпечує реєстрацію Email/Password з підтвердженням email, вхід, відновлення сесії та вихід. Тригер `readhub_auth_user_created` створює `profiles` і `user_access` для нового Auth UUID. Ім’я береться з перевірених користувацьких metadata; роль завжди починається з `user`, довіряти ролі з metadata клієнта не можна.

`profiles` містить ім’я, приватний `avatar_path` і `reminders_enabled`. `user_access` — роль `user/admin` та `is_blocked`. Призначення admin доступне лише довіреному оператору; публічного RPC зміни ролі немає. Функції `require_actor` та `is_admin` перевіряють актуальний доступ у БД. Прикладне блокування не є Auth ban і не відкликає JWT: захищені операції відмовляють за станом `user_access`, а власні профіль і статус лишаються доступними для пояснення відмови.

## Таблиці й основні зв’язки

У `public` — 13 прикладних таблиць, у `private` — службовий курсор нагадувань.

| Таблиця | Відповідальність і зв’язки |
| --- | --- |
| `profiles` | Один профіль на `auth.users.id`; видалення Auth каскадно прибирає профіль, якщо інші FK не блокують операцію |
| `user_access` | Один запис доступу на профіль; каскадне видалення разом із профілем |
| `clubs` | Клуб і його власник → profiles; архів позначається `archived_at` |
| `club_members` | Зв’язок клуб–профіль; ключ `(club_id,user_id)` забороняє дублікати |
| `join_requests` | Клуб, заявник, рішення та рецензент; одна pending-заявка на пару клуб–заявник |
| `club_books` | Книжкові записи конкретного клубу, статус і дати читання |
| `book_polls` | Голосування клубу, строк, переможець, скасування та використання вибору |
| `book_poll_options` | Книга й голосування того самого клубу; незмінні знімки назви та автора |
| `book_votes` | Один змінюваний голос на `(poll_id,user_id)`; варіант належить цьому голосуванню |
| `club_meetings` | Зустріч клубу: момент, timezone, формат, приватні деталі та версія розкладу |
| `club_discussions` | Тема клубу, автор, необов’язкова книга цього самого клубу |
| `club_discussion_comments` | Плоский список коментарів теми з авторством і станом видалення |
| `notifications` | Одержувач, клуб і ціль: заявка або зустріч із версією розкладу |
| `private.reminder_scan_state` | Обов’язковий singleton із курсором обходу пар зустріч–учасник |

Основні прикладні FK використовують `RESTRICT`, щоб видалення акаунта, клубу чи книги не знищувало історію непомітно. Складені FK перевіряють належність книги/варіанта/зустрічі правильному клубу або голосуванню. Переможець посилається назад на варіант свого голосування. Тому видалення Auth із залежними даними потребує окремої процедури, а не простого каскаду.

## RLS, RPC та серверні інваріанти

RLS і grants обмежують прямий доступ до таблиць. Бізнес-записи виконуються вузькими RPC: публічні обгортки — `SECURITY INVOKER`, привілейовані реалізації — `SECURITY DEFINER` у `private` із порожнім `search_path`. Вони самі перевіряють Auth, блокування, роль, членство та стан сутності. Схема `private` не публікується як API; службові helpers не відкриті клієнту. Доступ до профілю та аватарів має окремі обмежені операції.

| Суб’єкт | Основні права |
| --- | --- |
| Гість | Активні клуби та їхні книжкові полиці; без приватних зустрічей, тем і сповіщень |
| Заявник | Власні заявки; сама заявка не дає доступу до зустрічей чи обговорень |
| Учасник | Приватні дані свого клубу, участь у голосуванні й обговореннях |
| Власник | Керування власним активним клубом, полицею, голосуваннями, зустрічами й заявками |
| Admin | Адміністративний перегляд, блокування й модерація; без автоматичного права голосувати, писати як учасник чи редагувати чужі книги/зустрічі |

Обмеження CHECK/UNIQUE/FK захищають дані незалежно від React. RPC блокують акаунт і клуб перед залежними записами; голосування, зустріч або тема блокуються далі. Повторна перевірка після очікування запобігає запису з уже втраченими правами. Редагування зустрічей і обговорень потребує точного `updated_at`; застаріла версія отримує SQLSTATE `40001`. Тригер забезпечує монотонність версії з мікросекундами, клієнт зберігає її без округлення через Date.

## Клуби, заявки та архівування

`create_club` створює клуб і членство власника в одній транзакції. Заявки мають стани `pending/approved/rejected/cancelled`. Заявник змінює або скасовує лише pending; `review_join_request` перевіряє повноваження, забороняє розгляд власної заявки та додає членство при схваленні. Заблокованого заявника прийняти не можна. Рішення та відповідні сповіщення атомарні.

Власник не може вийти зі свого клубу або виключити себе. Вихід не видаляє історію заявок, голосів чи коментарів; approved означає історичне рішення, а поточне членство визначає тільки `club_members`. Передачу власності не реалізовано.

Архівування зберігає історію, відхиляє pending-заявки зі сповіщеннями, скасовує незавершені голосування та майбутні зустрічі. `restore_club` дозволений активному власнику/admin, повторний виклик для активного клубу не змінює його. Відновлення не відкриває скасовані події й не переглядає попередні рішення.

`list_clubs` повертає безпечну проєкцію: публічне ім’я власника, кількість членів, власне членство та похідні дані читання/розкладу. Архіви читаються за зв’язком користувача з клубом або адміністративними правами. Ім’я власника не відкриває приватні налаштування його профілю.

## Книги та голосування

Нові книги мають автора й статус `planned`. На клуб дозволена одна `current`; початок іншої книги вимагає явного рішення щодо попередньої — завершити або повернути до planned — і звіряння її ID. `completed` зберігає дату та історію. Успадковані записи можуть мати `is_migrated` і невідомого автора. Звичайне редагування метаданих не дозволяє підмінити клуб або службові поля. Перечитування та видалення книжкових записів не реалізовано.

Каталог обчислює поточну книгу з `club_books`; колонки `clubs.current_book` немає. Обкладинка — необов’язковий зовнішній HTTPS URL без credentials, а не Storage-об’єкт; зображення завантажує браузер, сервер не проксіює його.

Голосування створює власник щонайменше з двох різних planned-книг клубу. В один момент може бути одне невирішене голосування: минулий `ends_at` сам не закриває його. Варіанти лишаються заблокованими для зміни/початку читання до явної фіксації або скасування. Голосувати може чинний учасник до серверного строку; зміна вибору оновлює один запис. Вихід і повторний вступ не створюють другого голосу.

Власник фіксує лише лідера; за нічиєї обирає серед лідерів, за нульових результатів усі рівні. Переможець залишається planned. Початок його читання одноразово заповнює `selection_consumed_at`; повернення до planned не відновлює позначку. Показується вибір останнього зафіксованого голосування. Результати RPC містять кількості й власний вибір без списку виборців; сирі голоси видно лише їхнім авторам.

## Зустрічі й час

`club_meetings` зберігає `starts_at` як timestamptz, IANA timezone, формат online/offline/hybrid, адресу й HTTPS-посилання згідно з форматом. Власник активного клубу створює та змінює майбутні події через RPC. Минулі й скасовані зустрічі незмінні. Повні деталі читають власник, учасники й admin; гість та заявник їх не отримують.

Сервер перевіряє timezone, скінченність і майбутній момент, а клієнт передає ISO-час із UTC-зсувом. Форма відхиляє неоднозначні/неіснуючі місцеві години переходу часу; відображення розрізняє зону глядача й організатора. Незмінний час при редагуванні інших полів зберігає початкову точність.

`list_clubs` повертає лише найближчий момент/дату, без назви, адреси чи посилання події. `clubs.next_meeting` — незмінна історична дата, доступна як `legacy_next_meeting`, яка не підміняє новий розклад. При зміні `starts_at` тригер збільшує `schedule_version`; це ключ для актуальності нагадувань.

## Обговорення та коментарі

Власник, учасник і admin можуть читати теми. Писати може власник/учасник активного клубу; admin без членства лише модерує. Автор змінює свої записи; власник/admin можуть видалити чужі, але не переписати їх. Після виходу звичайний користувач втрачає доступ, його внесок зберігається. Архів незмінний, включно з модерацією.

Теми можуть стосуватися книги будь-якого статусу з того самого клубу. Тексти звичайні, без HTML; довжини й Unicode-пробіли узгоджено перевіряються клієнтом і сервером. Таблиці мають RLS без прямих клієнтських grants/політик: читання й зміни проходять тільки RPC-проєкціями. Автор і час задаються сервером.

Soft delete очищає title/body теми або body коментаря та фіксує, хто й коли виконав видалення. Відновлення тексту не передбачене. Видалена тема зникає зі списку, її коментарі недоступні; видалений коментар лишає заглушку без тексту та імені. Списки мають стабільне сортування й пагінацію; сервер повторно перевіряє доступ у statement вибірки. MVCC не відкликає вже отримані клієнтом дані чи раніший snapshot.

## Сповіщення, генератор і Cron

`new_request` та `request_decision` створюються lifecycle RPC. `meeting_reminder` посилається на зустріч і її `schedule_version`; CHECK відділяє ці цілі від заявок. Користувач бачить лише власні повідомлення. `list_my_notifications`, `get_my_unread_notification_count` і `mark_notification_read` не приймають довільного одержувача; прямий клієнтський UPDATE `read_at` заборонений. Повторне прочитання не змінює вже задану дату.

`private.generate_meeting_reminders(integer)` — довірений worker без публічної обгортки та клієнтського EXECUTE, включно із service_role. Він обробляє до 200 пар за замовчуванням (межі 1–1000): активний учасник активного клубу, `profiles.reminders_enabled=true`, нескасована зустріч із `now < starts_at <= now + 24 hours`. Поле `wants_reminders` заявки для цього не використовується; admin без членства не є одержувачем.

Advisory lock виключає одночасні генератори. Стабільний порядок user_access → clubs, SKIP LOCKED, повторна перевірка стану та унікальність `(meeting_id,recipient_id,meeting_schedule_version)` захищають від гонок і дублів. Обов’язковий singleton `private.reminder_scan_state` зберігає циклічний курсор: зайняті перші записи не блокують подальший обхід. Це не watermark часу; пропущені пари можуть бути перевірені знову. Один запуск — коротка транзакція. Тривалі блокування, зупинка worker або перевантаження можуть відкласти чи зірвати доставку до початку події.

Текст нагадування не містить приватної назви, адреси або посилання зустрічі. Актуальність і дозволений внутрішній перехід визначаються на читанні; старі повідомлення зберігаються після перенесення, скасування, виходу або вимкнення нагадувань. Непрочитаність залежить від `read_at`, а не актуальності. Реалізовано внутрішній центр повідомлень; email/push/Telegram-доставки нагадувань немає.

**Cron налаштований окремо від міграцій.** Репозиторій містить worker, але не створює job автоматично. За історично зафіксованим повідомленням власниці робочий період — 5 хвилин; у цій роботі віддалений стан не перевірявся. Конфігурація нового середовища описана тільки в [інструкції налаштування](supabase-setup.md); чинний job не дублюється й не змінюється під час запуску frontend.

## Storage та аватари

Приватний bucket `avatars` приймає JPEG/PNG/WebP до 1 MiB. Шлях — власний Auth UUID і випадкове ім’я; RLS перевіряє папку, `owner_id` та активність. Роль admin не надає доступу до чужих аватарів. Restrictive-політики не дозволяють стороннім permissive-політикам послабити захист.

Заміна завантажує новий шлях без upsert, потім прив’язує його до профілю й прибирає старий файл. Тригер перевіряє власника, наявність, MIME та розмір об’єкта. Профіль оновлюється зі звірянням попереднього шляху; видалення чинного прикріпленого файла захищене блокуванням профілю FOR UPDATE NOWAIT. Помилка cleanup може залишити власний неприкріплений файл; клієнт не прибирає чужі об’єкти.

Signed URL діє 120 секунд, оновлюється через 105 секунд і при поверненні у вкладку, зберігається лише в стані компонента. Виданий bearer URL може діяти до expiry після блокування акаунта. Клієнт перевіряє сигнатуру файлу; серверні обмеження MIME/метаданих не є незалежним декодуванням байтів. Завантаження й фізичне видалення виконуються Storage API, а не SQL-зміною `storage.objects`.

## Адміністративний доступ і межі перевірок

`admin_get_stats`, `admin_list_users`, `admin_list_clubs` і `admin_set_user_blocked` перевіряють активного admin у БД. Списки мають серверний пошук, фільтри, стабільне сортування та пагінацію. Проєкція користувача містить ID, ім’я, роль, блокування й дату профілю без email, Auth metadata, приватних налаштувань, паролів або токенів. Пряме читання чужих profiles цим не відкривається.

Блокування серіалізується advisory lock і повторною перевіркою прав; самоблокування та блокування останнього активного admin заборонені. Дані користувача й історія не видаляються, клуби автоматично не архівуються. Довірені зміни через Dashboard обходять цей RPC-протокол, тому збереження активного адміністратора лишається обов’язком оператора.

Архітектурні гарантії описують код, а не результати віддаленого тестування. [SQL-тести та сценарії конкурентності](../supabase/tests/README.md) збережені; підтвердження їх повного проходження немає. Актуальні локальні результати й повідомлений власницею стан deployment — у [журналі перевірок](verification.md).
