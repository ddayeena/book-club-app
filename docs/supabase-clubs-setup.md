# Етап 2: клуби, заявки та членство

## Ручне застосування

Перші дві Auth-міграції вже мають бути застосовані. Перевірте нові файли:

1. `202611100003_clubs_requests_tables.sql` — чотири таблиці, обмеження, індекси та RLS.
2. `202611100004_club_lifecycle_rpc.sql` — серверний життєвий цикл і безпечні проєкції.

Застосуйте їх у цьому порядку спочатку в окремому тестовому Supabase.
Застосунок не виконує міграції. Не запускайте перші дві міграції повторно.
Не додавайте схему private до Exposed schemas. Нових ключів або бібліотек не потрібно.
Власником SECURITY DEFINER-функцій має бути довірена адміністративна роль,
яка може читати таблиці в обхід RLS. Не передавайте їх у власність authenticated/anon.
Усі нові SECURITY DEFINER-реалізації розташовані в private. Публічні RPC — вузькі
SECURITY INVOKER-обгортки зі збереженими іменами/параметрами для React.
Приватні реалізації зберігають усі перевірки: саме перенесення до private не є
заміною авторизації. EXECUTE на них мають лише ролі, яким дозволені відповідні обгортки;
сирі require_actor/lock_club клієнту недоступні. anon отримує USAGE private і
EXECUTE лише list_clubs, без доступу до решти функцій. Схема private не є API-схемою.

Реальний застосунок (dev, build, preview) завжди використовує Supabase для клубів і заявок.
Застаріле `VITE_DATA_SOURCE=mock` у `.env.local` не вмикає локальні дані в браузері.
У Vitest залишено mock незалежно від локальних env; нові Supabase-сервіси тестуються
окремо з підміною клієнта. Старий REST-адаптер збережено для його наявних тестів.

Після застосування каталог буде порожнім. Створіть клуб через інтерфейс.
Жодних імпортів localStorage чи демонстраційних даних немає, локальні ключі не очищаються.
Повідомлення створюються в БД; інтерфейс повідомлень, email і Telegram не реалізовано.

## Доступ і операції

- Гість бачить активні клуби та публічне ім’я власника; точних адрес/посилань зустрічей у цій моделі немає.
- Архівні клуби читають пов’язані користувачі й admin; каталог показує активні,
  власник/admin також має список архіву.
- Учасники бачать список учасників через RPC, яка повертає лише ID, ім’я, аватар і дату вступу.
  Приватні налаштування profiles не відкриваються.
- Мої заявки завантажуються окремим запитом з фільтром applicant_id;
  вхідні заявки відкриваються на `/clubs/:clubId/requests` власнику/admin.
- Членство — `/clubs/:clubId/members`; власник не може вийти або виключити себе.
- Власник/admin редагує активний клуб і архівує його. Передавання власності та відновлення архіву не додано.
- Заявник редагує/скасовує лише pending. Скасування дає статус cancelled, фізичного видалення немає.
- Повторне подання після відмови/скасування/виходу/виключення зберігає історію.
- RPC review_join_request єдина виконує рішення та створює членство; власну заявку
  не може схвалити навіть admin. Заблокованого заявника не можна прийняти.
- Архівування відхиляє всі pending з поясненням і повідомляє заявників.
- Стан membership не зберігається окремо в заявці: approved означає історичне рішення,
  поточне членство визначається club_members.

Запис у clubs, club_members і join_requests із клієнта закритий навіть для прикладного admin.
RPC явно перевіряють Auth, блокування, власника/admin та допустимий стан.
Нові заявки й рішення створюють notifications у тій самій транзакції.
У notifications користувач може змінити лише read_at власного запису.

Усі операції над існуючим клубом блокують його рядок перед заявкою/членством.
Це серіалізує одночасне схвалення, скасування, вступ, вихід та архівування.
Унікальні обмеження додатково захищають pending-заявки й членство.
Архівування і вихід не видаляють історію; фізичне видалення профілів із залежностями
обмежене FK. Видалення Auth-акаунтів із клубними даними потребуватиме окремого процесу.

## Поточна книга та зустріч

current_book і next_meeting — тимчасове єдине джерело, сумісне з наявними формами.
next_meeting необов’язкова: NULL або порожній ввід означає невизначену дату;
нескінченні дати заборонені. Каталог ставить клуби без дати в кінець сортування,
головна не включає їх у перелік зустрічей.
У наступній версії їх потрібно перенести у club_books/meetings, змінити сервісний
адаптер і прибрати старі колонки в узгодженій міграції. Подвійного запису не вводимо.
members_count обчислюється з club_members, owner_name — із profiles, is_member — для Auth-користувача.

## Перевірки перед реальними даними

Запустіть `npm.cmd run lint`, `npm.cmd run test:run`, `npm.cmd run build`.
SQL-тести `supabase/tests/auth_rls.test.sql` та `club_lifecycle.test.sql`
запускайте лише на одноразовій локальній/тестовій БД після всіх міграцій
(у налаштованому Supabase CLI: `supabase test db`). Fixtures виконуються в транзакції з rollback.
JS-моки не підтверджують реальну RLS та виконуваність PL/pgSQL.

Ручний сценарій з трьома обліковими записами (власник, читач, admin):
створення двох клубів → заявка → редагування/скасування → повтор → відмова →
повтор → схвалення → список учасників → вихід → повторний вступ → виключення → архівування.
Перевірте notifications, перезавантаження сторінок, повторний вхід і перехід між акаунтами.
У двох незалежних SQL-сесіях тестової БД одночасно викличте review_join_request
для тієї самої pending-заявки, потім схвалення проти скасування/архівування:
друга операція повинна чекати на блокування й після першого commit перевірити новий стан;
членство та повідомлення не мають дублюватися. Ці конкурентні перевірки не замінює послідовний pgTAP-тест.

Секретні ключі не потрібні у React. Першого admin та його роль не змінюємо на цьому етапі.
