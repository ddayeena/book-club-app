# Supabase Auth — етап 1

Це інструкція першого етапу. Після реалізації другого етапу опис локальних клубів,
заявок і режиму mock нижче є історичним: див. `supabase-clubs-setup.md`.

## Що підготовлено

Supabase Auth (Email/Password), відновлення сесії, profiles, user_access,
ролі user/admin, блокування доступу, приватні налаштування нагадувань.
Адміністративної RPC та адмінпанелі немає. Нагадування не надсилаються.

## Ручне налаштування

1. Перевірте обидві версійні міграції у `supabase/migrations/`.
   Рекомендовано спочатку перевірити на окремому тестовому Supabase.
   Застосуйте `202611100001_auth_tables_and_rls.sql`, потім
   `202611100002_auth_user_bootstrap.sql` через SQL Editor або погоджений CLI-процес.
   Застосунок сам не запускає міграції. Не повторюйте вже застосовані файли.
2. У Authentication увімкніть Email/Password і залиште Confirm email увімкненим.
3. У URL Configuration задайте Site URL та дозволені адреси повернення:
   `http://localhost:5173/login`, за потреби `http://localhost:4173/login`,
   і точну HTTPS-адресу `/login` майбутнього хостингу.
   Використовується стандартне повернення з email-підтвердження з обробкою URL клієнтом.
   На хостингу потрібен SPA fallback на index.html.
4. Для реального надсилання листів налаштуйте SMTP та шаблон підтвердження.
   Ліміти пошти не обходьте вимкненням підтвердження.
5. Самостійно створіть `.env.local` за `.env.example`: URL проєкту і ключ
   `sb_publishable_…` з Dashboard. Не надсилайте секрети в чат.
   Перезапустіть Vite після зміни змінних. У VITE_* не додавайте secret/service_role.
6. Зареєструйте тестового користувача, підтвердьте email, перевірте вхід,
   перезавантаження, вихід і відмову входу без підтвердження.

## Перший адміністратор

Зареєструйте й підтвердьте потрібний обліковий запис. У Dashboard звірте його UUID
в Authentication → Users. У Table Editor для `public.user_access` знайдіть саме цей
`user_id`, змініть role з user на admin; is_blocked має залишатися false.
Оновіть сторінку, щоб перечитати роль. Призначення за email чи user_metadata немає.
У браузера немає дозволу змінювати user_access навіть із роллю admin.
До адмінпанелі ролями/блокуванням керує лише довірений оператор Dashboard;
він також відповідає за збереження хоча б одного активного admin.

`private.is_admin()` читає актуальну роль із БД та виключає заблоковані акаунти.
Схему private не додавайте до Exposed schemas. На першому етапі навіть admin
читає через API лише власний профіль/доступ — перегляд користувачів додамо з адмінпанеллю.
Заблокованому користувачу дозволено прочитати власний профіль і статус, щоб пояснити
відмову; редагування заборонене. Сам JWT при блокуванні не видаляється.

## Локальні дані

Старі ключі users/session/clubs/requests не очищаються й не мігрують.
Локальний ID не прирівнюється до Supabase UUID, навіть за однакової пошти.
Заявки фільтруються за поточним користувачем; відкладена операція відхиляється,
якщо за час очікування користувач змінився. Старі клуби залишаються публічним
локальним каталогом; редагувати можна лише записи з ownerId поточного користувача.

localStorage не є захищеним сховищем: людина з доступом до браузера/DevTools
може прочитати його напряму. На цьому етапі ізоляція стосується сценаріїв застосунку;
серверний захист клубів і заявок з’явиться після перенесення цих сутностей у БД.
Режим VITE_DATA_SOURCE=api не інтегрований із Supabase JWT; використовуйте mock.

## Перевірки

`npm run lint`, `npm run test:run`, `npm run build`.
У PowerShell із блокуванням npm.ps1 використовуйте npm.cmd.
Старі перевірки навчального Auth збережені на test-only адаптері
`src/test/legacyAuthService.js`; він не імпортується production-кодом.
Окремі тести перевіряють Supabase-сервіс, відновлення сесії, помилки та гонки.

`supabase/tests/auth_rls.test.sql` містить 13 pgTAP-перевірок реальних прав/тригера.
Запускайте лише на одноразовій локальній/тестовій БД після міграцій
(Supabase CLI `supabase test db` у налаштованому локальному середовищі).
Тест виконується в транзакції з rollback; не використовуйте production як тестову БД.
JavaScript-моки не доводять коректність віддаленої RLS: цей тест і ручна
перевірка email-потоку обов’язкові перед використанням реальних даних.
