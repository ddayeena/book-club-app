# Етап 5Б, частина 1: зустрічі клубів

Підготовлено `202611120009_club_meetings.sql` після міграцій 001–008.
Не містить Cron, змін notifications, email, push або автоматичних нагадувань.
`profiles.reminders_enabled` залишається налаштуванням для наступного етапу.

## Модель та доступ

- club_meetings зберігає точний starts_at (timestamptz), timezone, формат, адресу/HTTPS-посилання,
  опис, скасування та службові дати. Фізичного видалення через клієнт немає.
- Повні записи доступні активному власнику, чинним учасникам та активному адміністратору.
  Заявка, у тому числі історична, не надає доступу. Адміністратор без власності не керує зустрічами.
- Записи захищені RLS, клієнт має тільки SELECT. Запис виконується вузькими RPC:
  create_club_meeting, update_club_meeting, cancel_club_meeting.
  list_club_meetings повертає сторінки по 20 записів; get_club_meeting — один запис.
- Реалізації SECURITY DEFINER знаходяться у private із порожнім search_path.
  Публічні обгортки SECURITY INVOKER, гість не має EXECUTE.
- Для запису використовується чинний private.lock_book_owner: попри історичну назву він
  перевіряє активність, власність і неархівність клубу та блокує його рядок.
  Порядок: access actor → club → meeting; узгоджено з членством і архівуванням.
- Редагування та скасування перевіряють точний updated_at, включно з мікросекундами.
  Застарілий токен отримує 40001; форма пропонує перечитати дані.
  Нова версія монотонна навіть при дуже швидких оновленнях.
- Скасовані та минулі зустрічі не змінюються. Архівування через наявний RPC запускає
  тригер, який скасовує майбутні зустрічі; минула історія залишається.
  Існуючі повідомлення заявок і скасування голосувань збережено.

## Старий розклад і каталог

clubs.next_meeting не видаляється і не переноситься у фіктивні зустрічі.
На час атомарного переходу міграція бере ACCESS EXCLUSIVE на clubs, тому запускати
її краще без активного редагування клубів. Помилка відкочує всю транзакцію.
create_club/update_club більше не записують його; непорожній старий payload відхиляється
явною помилкою 55000, щоб старий клієнт не втрачав введені дані мовчки.
Історична дата залишається при звичайному редагуванні клубу.
Тригер clubs_legacy_meeting_readonly також відхиляє фактичну зміну старої дати
та INSERT з непорожньою датою. Це захищає від старих тіл функцій, що вже виконувалися
під час переходу. Тести імітують успадковану дату тільки через привілейовані fixtures
із тимчасовим вимкненням цього тригера в одноразовій БД, усередині ROLLBACK.

list_clubs повертає:
- next_meeting — найближчу дату нової нескaсованої майбутньої зустрічі в зоні організатора;
- next_meeting_at — її точний момент;
- legacy_next_meeting — стару дату окремо, з позначкою «час не уточнено».

Для архівного клубу найближчої нової зустрічі немає. Каталог не повертає назву, опис,
місце чи посилання зустрічі. Старі дати не підміняють новий розклад і не впливають
на сортування як нібито підтверджені майбутні зустрічі.
Форма клубу більше не має поля дати; meetings_per_month залишається загальною частотою.

## React та час

Маршрути:
- /clubs/:clubId/meetings
- /clubs/:clubId/meetings/new
- /clubs/:clubId/meetings/:meetingId
- /clubs/:clubId/meetings/:meetingId/edit

Список має категорії, URL-фільтр і пагінацію, повторне завантаження та стани помилок.
Деталі показують місцевий час глядача й час у зоні організатора.
Форма вводить час у зоні браузера, передає ISO UTC із Z і показує попередній перегляд.
При редагуванні інших полів незмінний час зберігається з оригінальною точністю,
включно з секундами/мікросекундами та timezone. Нова введена дата перетворюється у UTC.
Каталог сортується за точними моментами next_meeting_at, картки й календарний блок
показують дату в зоні глядача; дата організатора не підміняє місцевий день.
Сервер перевіряє зсув у payload, скінченність, майбутній момент і відому timezone.
Неіснуюча та неоднозначна година переходу часу відхиляється у формі:
у першій версії потрібно вибрати однозначний час поза цим інтервалом.
Окремого селектора часових поясів і нових бібліотек немає.

Підтвердження скасування повторно використовує існуючий компонент; Escape закриває,
фокус повертається на кнопку. Повторні натискання на збереження/скасування блокуються.
Після оновлення сторінки дані перечитуються через RPC.
Зміна акаунта перемонтовує приватні сторінки, незавершені читання скасовуються.

## Перевірки перед застосуванням

1. Спочатку застосувати 009 в одноразовому тестовому Supabase з 001–008.
2. Виконати `supabase/tests/club_meetings.test.sql` та попередні SQL-набори.
   Тести з fixtures завершуються ROLLBACK; вони не призначені для основної БД.
   club_lifecycle.test.sql адаптовано до відмови від старого редактора дати після 009.
3. Перевірити в двох SQL-сесіях: одночасне редагування з одним updated_at,
   скасування проти редагування, архівування проти створення, вихід учасника.
   pgTAP перевіряє застарілий токен послідовно; це не доказ реального паралельного виконання.
4. Перевірити власника, учасника, стороннього, заявника, адміністратора і заблокованого
   зі звичайними JWT; не перевіряти RLS лише через привілейовану роль SQL Editor.
5. Перевірити реальні timezone зі старої/нової версії браузера (Europe/Kiev і Europe/Kyiv),
   зимовий/літній час, F5, мобільний екран і клавіатуру.
6. Перевірити каталог після створення/перенесення/скасування; остання зустріч минула —
   після повторного завантаження найближча дата зникає.
7. Звичайне редагування клубу не змінює стару дату, книжкову полицю, заявки чи голосування.
8. Розгортати новий React після застосування 009; попередні міграції повторно не запускати.

Локально виконуються ESLint, Vitest і production build. SQL-тести та реальне застосування
міграції потребують окремої ручної перевірки; без запуску SQL вони не вважаються пройденими.

Додаткових розширень для 009 не потрібно: gen_random_uuid, timestamptz і
pg_timezone_names — чинні можливості PostgreSQL. pgTAP потрібний лише для SQL-тестів.
Додаткових налаштувань Storage, Cron, Exposed schemas або RLS у Dashboard немає.
