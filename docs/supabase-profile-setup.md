# Етап 5А: профіль, мої клуби та приватні аватари

Маршрути `/profile` і `/my-clubs` захищені наявним RequireAuth. Меню користувача містить
переходи до обох сторінок; адміністративні посилання не повертаються.
Профіль не монтує провайдери клубів і заявок та не залежить від їхнього завантаження.
Нагадування лише зберігаються: email/Telegram не надсилаються.

## Міграція та ручні дії

1. Перегляньте `supabase/migrations/202611120008_profile_avatars.sql` після 001–007.
2. Спочатку застосуйте 008 вручну в окремому тестовому Supabase. Міграція атомарна й не переписує
   старі профілі/шляхи. Якщо bucket avatars уже існує, міграція зупиниться: спочатку перевірте його
   дані та конфігурацію, не видаляйте їх заради повторного запуску.
3. Виконайте `supabase/tests/profile_avatars.test.sql` у цьому одноразовому проєкті з pgTAP.
   Тест створює фіктивних користувачів та метадані Storage і завершується ROLLBACK.
   Не виконуйте ці fixtures в основній БД. Прямі SQL-зміни метаданих — лише тестові,
   вони не завантажують і не видаляють справжні файлові об’єкти.
4. Після перевірки та резервного копіювання застосуйте 008 вручну в розробницькому проєкті.
   Попередні міграції повторно не запускайте. Новий клієнт аватарів розгортайте після 008.
5. `.env.local`, ключі, Auth email confirmation і Exposed schemas не змінюються.
   service_role/secret key у React не потрібний. Нових бібліотек немає.
   Створювати bucket чи додавати політики вручну в Storage Dashboard не потрібно:
   це робить 008. Після застосування лише перевірте Private, MIME та ліміт 1 MB.
   Міграція відмовиться виконуватися, якщо RLS Storage вимкнено; клієнтські UPDATE/DELETE
   налаштувань avatars заборонені навіть за наявності широких permissive-політик.

## Безпека та зберігання

- Bucket avatars приватний; Storage API обмежує MIME image/jpeg, image/png, image/webp і розмір
  1 048 576 байтів. Клієнт додатково перевіряє MIME, розмір і початкові сигнатури JPEG/PNG/WebP.
  Серверні MIME-обмеження та перевірка метаданих не є декодуванням зображення:
  незалежної перевірки байтів на сервері немає. Для такої гарантії потрібен окремий
  довірений обробник завантаження; SQL/RLS не читають вміст файлів Storage.
- Шлях — `<auth.uid>/<randomUUID>.jpg|png|webp`, оригінальне ім’я файла не використовується.
  RLS перевіряє і папку, і owner_id, і активність акаунта; глобальна роль admin не дає доступу
  до чужих фото. Restrictive-політики захищають avatars також від сторонніх permissive-політик.
- Аватари незмінні за конкретним шляхом. Заміна — новий upload з upsert:false, а не UPDATE старого
  об’єкта. Тому старий файл залишається чинним до успішного збереження нового посилання.
- Існуючі RLS profiles та колонкові grants залишаються. Новий приватний тригер перевіряє
  змінений avatar_path: власну папку, наявність завантаженого об’єкта, owner_id, MIME й розмір.
  URL, чужі та відсутні файли не можна прив’язати. Незмінні старі значення не переписуються.
- Оновлення фото перевіряє попередній avatar_path у WHERE: застаріла вкладка не перезапише нове
  фото. Після успішного збереження виконується прибирання старого файла. При помилці оновлення
  видаляється лише новий неприкріплений файл; чинний аватар захищено від видалення політикою.
- Видалення: спочатку avatar_path=NULL, потім Storage remove. При помилці cleanup збережений
  стан не відкочується, користувач отримує попередження; неприкріплений старий файл може залишитися.
  Після втрати мережі або зміни акаунта можливі власні неприкріплені файли; чужі файли клієнт не чистить.
- Захист referenced-файла отримує власний рядок профілю FOR UPDATE NOWAIT. Якщо профіль
  зайнятий іншою транзакцією, видалення не дозволяється, а cleanup може показати попередження.
  Це уникає взаємного очікування: Storage API може вже тримати замок об’єкта перед RLS,
  тоді як тригер прив’язки після замка профілю отримує FOR SHARE на об’єкті.
- Signed URL діє 120 секунд, поновлюється через 105 секунд і при поверненні у вкладку.
  URL зберігається лише в стані компонента, не в БД/localStorage. При помилці — ініціали,
  поновлення повторюється з паузою. Зміна користувача чи шляху скидає попереднє зображення.
- Блокування забороняє нові Storage-операції та підписання. Уже видане signed URL може
  працювати до закінчення свого короткого строку; миттєвого відкликання bearer URL немає.

Поле дати реєстрації береться з власного Auth user.created_at, а created_at профілю — запасний варіант.
Профіль зберігає тільки name, reminders_enabled і, при явній зміні фото, avatar_path.
Після успіху AuthProvider перечитує дані, а меню оновлює ім’я та фото.

«Мої клуби» використовує наявні ownerId, isMember та archivedAt з list_clubs/ClubsProvider.
Власник не дублюється серед інших членств; архівні клуби виділено окремо. Доступ адміністратора
до чужого каталогу або доступ через історію заявки не вважається членством.
Локальні акаунти та клуби не імпортуються, наявні локальні дані не видаляються.

## Ручна перевірка

- Два акаунти: власний профіль редагується, чужий — ні; ID, role, is_blocked і дати незмінні.
- Реальні Storage upload: JPEG/PNG/WebP, рівно 1 MB, понад 1 MB, SVG, підроблені MIME/розширення.
  Bucket перевіряє MIME через Storage API; SQL metadata fixtures не перевіряють файлові байти.
- Чужа папка/owner_id, прив’язка чужого або відсутнього файла, спроба зберегти signed URL замість шляху.
- Завантаження, заміна, видалення, скасування вибору; помилки upload/profile update/cleanup.
  Переконайтеся, що старе фото не втрачається до успіху заміни.
- Дві вкладки одночасно замінюють фото; видалення одночасно з прив’язкою; змінений файл не губиться.
- Signed URL після 120 секунд, довга неактивна вкладка, F5, помилка картинки, перемикання акаунтів.
- Заблокований акаунт із чинним JWT не може завантажувати чи видаляти файли. Старе URL може
  читатися до expiry — це очікувана властивість підписаних посилань.
- Профіль працює при помилці каталогу/заявок; нове ім’я відображається після збереження.
- «Мої клуби»: власні, учасницькі й архівні; без дублів, чужих admin-visible клубів і клубів лише з історії заявок.
- Мобільний екран, довгі імена, клавіатура, фокус форми, повторне завантаження та подвійне натискання.

Локально: `npm.cmd run lint`, `npm.cmd run test:run`, `npm.cmd run build`.
Фактичні Storage API, RLS та конкурентність перевіряються окремо після застосування міграції.
