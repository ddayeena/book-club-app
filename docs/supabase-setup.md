# Налаштування нового середовища Supabase

Це інструкція відтворення, а не команда повторно налаштувати чинний ReadHub. Міграції, cleanup та демонстраційний reset автоматично під час запуску застосунку не виконуються. Не повторюйте вже застосовані міграції.

## Порядок налаштування

1. Створіть окремий Supabase-проєкт для нового середовища. Перевірте ланцюг міграцій спочатку в одноразовій тестовій БД.
2. Застосуйте всі файли `supabase/migrations/` у порядку імен, **001–012**. Це джерело визначень таблиць, індексів, RLS, тригерів і RPC; вручну відтворювати їх із документації не потрібно.
3. Увімкніть Auth Email/Password із Confirm email. Задайте Site URL свого frontend і дозволені повернення `/login`: локально `http://localhost:5173/login`, для preview за потреби `http://localhost:4173/login`, для Vercel — точну HTTPS-адресу свого deployment. Для реальної пошти налаштуйте SMTP та шаблони; не вимикайте підтвердження для обходу лімітів.
4. Створіть локальний `.env.local` за `.env.example`: `VITE_SUPABASE_URL` і `VITE_SUPABASE_PUBLISHABLE_KEY`. Використовується publishable key `sb_publishable_…`. Серверні secret/service_role ключі в `VITE_*` заборонені. Ті самі публічні значення задаються в налаштуваннях frontend-хостингу для відповідного середовища.
5. `private` не додавайте до Exposed schemas. Довірені власники SECURITY DEFINER-функцій та обмежені grants визначаються міграціями; не передавайте функції у власність клієнтських ролей.
6. Міграція 008 сама створює приватний bucket `avatars` із MIME JPEG/PNG/WebP та лімітом 1 MiB. Не створюйте другий bucket і не послаблюйте політики вручну. Зображення додаються через Storage API.
7. Для автоматичних внутрішніх нагадувань окремо налаштуйте довірений Cron-виклик `select private.generate_meeting_reminders(200);`. За історичною документацією робочого проєкту період — кожні 5 хвилин. Міграція 011 не створює Cron-job. На новому середовищі звірте конфігурацію й права виконавця; у чинному проєкті не створюйте дубль і не змінюйте наявний job. Принцип роботи описаний у [backend-архітектурі](backend-architecture.md).
8. Зареєструйте та підтвердьте власний акаунт. Для призначення admin звірте його UUID у Dashboard → Authentication → Users, знайдіть той самий `user_id` у `public.user_access`, задайте `role=admin`, `is_blocked=false` й оновіть сторінку. Зберігайте принаймні одного активного admin; клієнтського RPC зміни ролі немає. Для звичайної роботи демонстраційний reset не потрібен.

## Карта міграцій

Модель даних і правила всіх модулів зібрані в [backend-architecture.md](backend-architecture.md).

| Міграції | Модуль |
| --- | --- |
| 001–002 | Auth, профілі, доступ і bootstrap |
| 003–004 | Клуби, заявки, членство й lifecycle RPC |
| 005 | Книжкова полиця |
| 006 | Голосування |
| 007 | Адмінпанель |
| 008 | Профіль і приватні аватари |
| 009 | Зустрічі |
| 010 | Відновлення клубів |
| 011 | Центр сповіщень і генератор нагадувань |
| 012 | Обговорення та коментарі |

## Перевірки й демонстрація

Міграції відтворюють структуру, а не демонстраційні записи чи налаштування Vercel/Auth/Cron. [Демонстраційні файли](../supabase/demo/README.md) — окрема процедура для свідомого очищення та повторного наповнення. У поточному проєкті дані й новий admin уже створені за підтвердженням власниці.

Frontend-перевірки не замінюють pgTAP, реальні JWT, Storage upload або конкурентні SQL-сесії. [Порядок SQL-тестування](../supabase/tests/README.md), [фактичний статус](verification.md). На основній БД тестові fixtures не запускайте.
