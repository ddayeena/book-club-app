# Етап 3А: книжкова полиця

Голосування не реалізовано. Нових бібліотек, API пошуку, Storage-бакетів або ключів немає.
Публічна сторінка активного клубу: `/clubs/:clubId/books`. Архіви підпорядковані
наявним правам доступу до клубу (власник, admin, учасник або власна історія заявок).
Змінювати книги може лише активний власник неархівного клубу; роль admin сама
по собі не дає права змінювати чужі книги.

## Міграція

Після вже застосованих 001–004 перевірте й вручну застосуйте
`202611110005_club_books.sql`. Старі міграції не редагуються й не запускаються повторно.
Спочатку використайте окремий тестовий Supabase, а не базу з потрібними даними.

У межах однієї транзакції міграція:

1. Блокує clubs від конкурентних записів на час переходу.
2. Створює club_books, унікальність однієї current-книги, RLS та RPC.
3. Переносить усі непорожні current_book, включно з архівними, зі збереженням
   оригінальної назви. Порожній рядок означає відсутність книги. Автор, обкладинка,
   опис і дата початку невідомі: вони не вигадуються.
4. Перевіряє відповідність кожної старої назви перенесеному запису.
5. Замінює залежні private.create_club/update_club/list_clubs.
6. Прибирає стару колонку без CASCADE. Невідома залежність або помилка відкочує
   транзакцію; старі дані залишаються. PostgREST отримує повідомлення оновити schema cache.

Проводьте оновлення з короткою зупинкою записів і узгодженим розгортанням нового
React-клієнта. Старі відкриті вкладки потрібно перезавантажити: спроба передати
непорожній current_book старим способом відхиляється явно, а не ігнорується.
Перед оновленням збережіть контрольну вибірку club id → current_book у безпечному
місці поза Git. Після нього порівняйте її з current-записами club_books.
Не відновлюйте стару колонку вручну й не запускайте міграцію двічі.

Каталог продовжує отримувати JSON current_book із list_clubs, але значення
обчислюється з club_books. ReadingStatusBadge, картки, статистика й пошук
зберігають currentBook. Звичайна форма клубу більше не записує книгу.
Mock-оновлення клубу зберігає старе значення книги для попередніх тестів.

## Читання

- Нові книги завжди planned; автор обов’язковий.
- Перенесені записи мають захищений is_migrated і можуть мати NULL автора.
- Збереження метаданих не дозволяє передати status, is_migrated або інший club_id.
- Почати можна planned-книгу. За наявності current власник явно обирає:
  завершити попередню або повернути її до planned.
- RPC звіряє очікуваний ID попередньої книги. Застаріле рішення не замінює
  вже змінену іншим запитом current-книгу.
- Завершення зберігає історію й дату; перечитування та видалення поки не додані.
- Усі зміни блокують рядок клубу, узгоджено з архівуванням і наявними операціями.
- Публічні RPC — SECURITY INVOKER, привілейовані реалізації — у private з явною
  авторизацією та порожнім search_path. private не додавайте до Exposed schemas.

Обкладинка — необов’язковий HTTPS URL без логіна/пароля. React перевіряє адресу,
не використовує HTML із даних і показує заглушку при помилці. Зображення має
no-referrer і lazy-loading. Сторонній хост зображення все одно бачить IP запиту;
не розміщуйте секретні дані в URL. Сервер не завантажує й не проксіює картинки.

## Перевірки

`npm.cmd run lint`, `npm.cmd run test:run`, `npm.cmd run build`.
Новий SQL-тест — `supabase/tests/club_books.test.sql`, лише для одноразового
тестового проєкту після всіх п’яти міграцій. Він перевіряє RLS, EXECUTE, автора,
підміну службових полів, читання, явну заміну, стороннього/admin/blocked та архіви.
Fixtures відкочуються ROLLBACK. JavaScript-тести не доводять роботу PostgreSQL.

Окремо перевірте сам перехід: у тестовому проєкті з 001–004 створіть активний та
архівний клуб зі старими current_book (наприклад, назва з лапками/українськими
символами), ще один клуб без книги; застосуйте 005 і звірте назви та NULL авторів.
Потім перевірте каталог, фільтр «зараз читають», головну, старі маршрути, додавання,
редагування, обидва варіанти заміни current та завершення після F5.
У двох SQL-сесіях перевірте конкурентний старт двох книг і старт проти архівування:
результат має містити не більше однієї current, зі збереженою історією.
Авторизація, заявки, членство та їхні попередні SQL-тести мають залишитися працездатними.
