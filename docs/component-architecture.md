# Архітектура ReadHub

Цей документ описує frontend завершеної реалізації. Серверна модель і права зібрані в [backend-архітектурі](backend-architecture.md). Історія навчальних етапів відділена в [описі проєкту](project-plan.md); налаштування — в [інструкції Supabase](supabase-setup.md), фактично виконані перевірки — в [журналі](verification.md).

## Потік даних

```text
Маршрутна сторінка / форма
  → хук або провайдер
  → src/services/*Service.js
  → Supabase Auth / PostgREST / RPC / Storage
  → PostgreSQL: обмеження, RLS, приватні реалізації RPC
```

`src/domain/` містить чисті функції валідації, відбору та форматування. Компоненти в `src/components/` відповідають за предметні блоки й спільні елементи інтерфейсу. Контексти оголошені в `src/context/`, власники спільного стану — у `src/providers/`. Сервіси відділяють модель інтерфейсу від SQL-полів і параметрів RPC.

## Маршрути й провайдери

`App.jsx` задає маршрути. `SessionLayout` огортає їх `AuthProvider` та `AuthGate`. Основна й адміністративна гілки мають окремі макети; `RequireAuth` і `RequireAdmin` перевіряють доступ перед захищеним вмістом. Сервер повторно перевіряє права незалежно від цих компонентів.

Основний `AppLayout` підключає `NotificationsProvider`. Для `/profile` і `/notifications` він не монтує `ClubsProvider` та `ClubSelectionProvider`, тому помилка каталогу не блокує особисті дані. Інші основні маршрути отримують каталог і вибір клубу. `RequestsProvider` із ключем поточного акаунта вмикає читання заявок лише для маршрутів, яким вони потрібні: головної, заявок і деталей клубу.

Адміністративна гілка використовує `AdminLayout` під `RequireAdmin` й не залежить від завантаження основного каталогу або заявок. Пов’язані сторінки завантажуються сімома lazy-групами: [деталі](frontend-code-splitting.md).

| Маршрути | Призначення |
| --- | --- |
| `/`, `/clubs`, `/clubs/:clubId` | Головна, каталог, деталі клубу |
| `/login`, `/register`, `/logout` | Auth |
| `/profile`, `/my-clubs`, `/notifications` | Особисті дані, членство, сповіщення |
| `/requests`, `/requests/new`, `/requests/:requestId`, `/requests/:requestId/edit` | Заявки користувача |
| `/clubs/new`, `/clubs/:clubId/edit`, `/clubs/:clubId/members`, `/clubs/:clubId/requests` | Керування клубом і вступом |
| `/clubs/:clubId/books`, `/clubs/:clubId/polls`, `/clubs/:clubId/polls/:pollId` | Читання та голосування |
| `/clubs/:clubId/meetings` та дочірні new/detail/edit | Зустрічі |
| `/clubs/:clubId/discussions` та дочірні new/detail/edit | Теми й коментарі |
| `/admin`, `/admin/users`, `/admin/users/:userId`, `/admin/clubs`, `/admin/clubs/:clubId` | Адміністративний розділ |

## Власники стану

| Дані | Власник / джерело |
| --- | --- |
| Сесія, профіль, роль і блокування | AuthProvider; Supabase Auth, profiles, user_access |
| Каталог і вибір клубу | ClubsProvider, ClubSelectionProvider; list_clubs |
| Заявки поточного акаунта | RequestsProvider; Supabase-сервіс заявок |
| Лічильник сповіщень | NotificationsProvider; окремі notification RPC |
| Пошук, фільтри й пагінація | URL-параметри відповідних сторінок |
| Чернетки, помилки, стан підтвердження | Локальний стан форми/компонента |
| Книги, голосування, зустрічі, теми, admin-дані | Сервіси та локальні ресурси відповідних сторінок |

Похідні списки й лічильники обчислюються з вихідних даних. Застарілі читання скасовуються або відкидаються; стан ізолюється при зміні акаунта. Помилки запису не повинні прибирати введену чернетку. Зустрічі й обговорення використовують очікувану серверну версію `updated_at` для виявлення конфліктів.

## Серверна модель

Міграції 001–012 визначають 13 прикладних таблиць `public` і службовий курсор `private.reminder_scan_state`. Профіль посилається на реальний Auth UUID; ролі не беруться з користувацьких metadata. Власник клубу є його учасником. Книги зберігаються в `club_books`, актуальний розклад — у `club_meetings`; каталог повертає похідні значення.

Клієнтські зміни бізнес-сутностей проходять через вузькі RPC з перевіркою активності, ролі, членства, стану клубу й блокуваннями. Приватні `SECURITY DEFINER` реалізації мають порожній `search_path`; публічні обгортки — `SECURITY INVOKER`. Профіль і Storage мають власні обмежені операції. Обговорення повертаються лише RPC-проєкціями, без загального клієнтського доступу до сирих таблиць.

## Тестові адаптери

Production та звичайний dev використовують Supabase незалежно від старих `VITE_DATA_SOURCE` значень. У Vitest залишені `MockClubsProvider`, mock/REST-сервіси, `src/data/` та `src/test/legacyAuthService.js` для ізольованих перевірок і навчальних регресій. Вони не означають використання локальної авторизації в розгорнутому ReadHub. Відмова Supabase не підставляє локальні дані.
