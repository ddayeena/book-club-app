# Етап 4: адмінпанель ReadHub

Маршрути: `/admin` (статистика), `/admin/users`, `/admin/users/:userId`, `/admin/clubs`, `/admin/clubs/:clubId` (деталі). Використовуються чинні AuthProvider,
profiles та user_access. Каталог клубів і заявки на адміністративних маршрутах не завантажуються.
Нових таблиць, бібліотек, ключів, Storage або Realtime-налаштувань немає.

Статистика показує основні картки, переходи до списків і фільтрів, детальні лічильники та
співвідношення статусів заявок без бібліотеки графіків. Усі показники надходять з одного admin_get_stats.
Деталі клубу повторно використовують безпечну проєкцію list_clubs, включно з created_at:
нової RPC, зміни RLS або міграції 008 не потрібно. Чинний каталог повертає всі доступні клуби,
і потрібний запис вибирається на клієнті; для поточного масштабу курсової цього достатньо.
При поверненні з деталей зберігаються q, state і page в URL. Архівування використовує чинний archive_club.

Деталі користувача не потребують міграції 008: спочатку admin_list_users перевіряє адміністративну
роль у БД; пошук повного ID уточнюється точним збігом і за потреби наступними сторінками.
Повертаються лише ім’я, ID, роль, блокування та created_at профілю як дата реєстрації.
Власні клуби читаються з clubs за owner_id, членство — з club_members за user_id з вкладеними
основними даними clubs. Це дозволяють уже наявні RLS 003: активний admin проходить manages_club;
загальні права profiles, user_access та club_members не розширюються. Читання клубів має пагінацію.
Якщо адміністративний RPC відмовляє, запити клубів не виконуються. Будь-яка помилка читання
членства відображається як помилка сторінки, а не як нуль клубів.
Членства враховують власні клуби, але список участі в інших клубах їх виключає. Активні й архівні
клуби враховуються однаково; членство після виходу вже відсутнє й не входить у лічильник.
Посилання ведуть на адміністративні деталі клубу, назад до користувачів зберігаються q/role/state/page.
Блокування повторно використовує admin_set_user_blocked, без зміни ролей або Auth ban.

На деталях клубу розділ «Учасники клубу» повторно використовує list_club_members із 004.
RPC дозволяє читання активному admin через manages_club, включно з архівними клубами.
Список показує тільки ім’я, посилання на профіль і клубну роль за owner_id; дій зміни членства немає.
Завантажується по 20 записів із перевіркою наступної сторінки одним додатковим рядком,
стабільним сортуванням joined_at/user_id та кнопкою «Показати більше». Помилка наступної сторінки
не приховує вже отриманих учасників. Оновлення списку заново завантажує першу сторінку.
Статус блокування ця RPC не повертає: окремих запитів для кожного учасника або завантаження
всіх акаунтів заради статусів немає. Стан акаунта доступний на сторінці профілю користувача.
Додаткові RPC, розширення RLS або нова міграція для цього розділу не потрібні.

## Ручне застосування

1. Перевірте `supabase/migrations/202611110007_admin_panel.sql` після вже застосованих 001–006.
   Попередні міграції не змінюйте й повторно не запускайте.
2. Спочатку застосуйте 007 в окремому тестовому Supabase. Міграція виконується однією транзакцією.
3. У цьому одноразовому проєкті виконайте `supabase/tests/admin_panel.test.sql` з pgTAP,
   а також попередні SQL-тести. Тести створюють Auth-користувачів, клуб, заявку та голосування,
   змінюють ролі й блокування, архівують клуб і завершуються ROLLBACK.
   Для перевірки останнього адміністратора тест тимчасово блокує також інших адміністраторів
   у тестовій БД. Не запускайте цей файл на основному проєкті, навіть попри ROLLBACK.
4. Після перевірки зробіть резервну копію основної БД та вручну застосуйте 007, потім оновіть клієнт.
   `.env.local` змінювати не потрібно. Не додавайте private до Exposed schemas.
5. Наявний незаблокований admin отримує доступ. Першого/додаткових адміністраторів, як і раніше,
   призначають вручну через Dashboard. UI та RPC не дозволяють змінювати ролі.

## Серверний захист

- `admin_get_stats` повертає всі лічильники одним запитом і одним знімком даних.
- `admin_list_users` повертає лише ID, ім’я, роль, блокування й дату профілю.
  Email, Auth metadata, налаштування нагадувань, паролі й токени не повертаються.
- `admin_list_clubs` повертає безпечні основні дані, ім’я власника й кількість членств.
- Списки мають серверні фільтри, стабільне сортування, total і пагінацію (клієнт 20,
  сервер не більше 50 записів). Пошук нечутливий до регістру, `%`/`_` не є шаблонами.
- Публічні RPC — SECURITY INVOKER; реалізації — SECURITY DEFINER у private з порожнім search_path.
  EXECUTE дозволений authenticated, але кожна реалізація перевіряє активного admin у БД.
  anon і PUBLIC не отримують EXECUTE; сирий require_admin закритий.
- RLS профілів не розширено: навіть admin читає через прямий API тільки свій профіль і user_access.
  Нових прямих UPDATE-прав немає. Наявні клубні права адміністратора збережені.
- admin_set_user_blocked приймає лише ID та boolean. Забороняє самоблокування й блокування
  останнього активного admin. Один транзакційний advisory lock серіалізує ці операції до отримання
  блокувань рядків; права повторно перевіряються після очікування замка.
- За наявності іншого активного адміністратора правило останнього захищає інваріант додатково:
  останній не може заблокувати себе, а заблокований admin не може блокувати інших.
- Ручні зміни через Dashboard/довірений SQL обходять протокол RPC. Не блокуйте останнього
  адміністратора й не змінюйте ролі паралельно з такими операціями.

Блокування не видаляє профіль, клуби, членство, заявки чи голоси та не архівує клуби автоматично.
Це прикладне блокування user_access, а не Supabase Auth ban: воно не відкликає вже видані JWT.
Захищені операції перевіряють стан у БД. Публічні дані активних клубів залишаються публічними.
Власні профіль і access доступні для пояснення відмови згідно з наявними RLS.
Інтерфейс перечитує права при focus/visibilitychange та відмові 42501; після F5 роль відновлюється
з БД до показу адмінпанелі. Миттєва синхронізація неактивних відкритих вкладок не реалізована.

Архівування використовує наявний archive_club: збереження історії, відхилення pending-заявок,
повідомлення заявникам і скасування незавершеного голосування залишаються атомарними.
Учасники на дашборді: memberships — рядки членства, unique_members — різні user_id;
враховано також власників і архівні клуби. Користувачі — профілі з user_access, не старі локальні акаунти.

## Перевірки після застосування

- Гість і user: прямі URL та RPC недоступні. Admin: F5, меню, усі три сторінки.
- Каталог/заявки: штучна помилка цих запитів не повинна блокувати `/admin`.
- Пошук, усі фільтри, сторінки, порожній і завеликий номер сторінки; URL відновлюється після F5.
- Блокування/розблокування, підтвердження та Escape/скасування, подвійне натискання, мережеві помилки.
- Самоблокування й останній admin, заблокований admin з чинним JWT, зміна ролі через Dashboard.
- Архівування чужого клубу з pending-заявкою та голосуванням: перевірити історію й notifications.
- Вузький екран, довгі імена та назви; адміністратор бачить тільки дозволені дані.
- Регресії Auth, клубів, членства, книжкової полиці й голосувань.

Конкурентну перевірку виконайте двома SQL-сесіями лише в тестовій БД: два активні admin
одночасно намагаються заблокувати один одного через RPC. Друга операція після очікування
повинна перечитати права й отримати відмову, якщо її автор уже заблокований; щонайменше один
активний admin залишається. Також перевірте два блокування одного користувача й одночасне
блокування/розблокування. Послідовні pgTAP-тести не підтверджують ці конкурентні сценарії.

Локально: `npm.cmd run lint`, `npm.cmd run test:run`, `npm.cmd run build`.
SQL-тести й перевірка реальних прав Supabase потребують окремого виконання.
