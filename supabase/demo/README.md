# ReadHub: відтворення демонстрації

**Поточний стан:** власниця підтвердила успішне створення демонстраційних даних і роботу нового адміністратора. Для запуску сайту ці файли повторно виконувати не потрібно.

Нижче — процедура свідомого повного повторного створення демонстрації. `01_cleanup.sql` видалить усі прикладні записи, зокрема профіль і роль нового адміністратора. Подальший `auth-demo.mjs` видалить **усі** Auth-акаунти, включно з цим адміністратором. Скрипт створює лише звичайних користувачів: після повного reset адміністратора доведеться зареєструвати й призначити заново. На поточній заповненій БД cleanup не запускайте для звичайної перевірки чи оновлення документації.

Для нового свідомого циклу спочатку виконується `01_cleanup.sql`, потім два кроки нижче. Потрібні `auth-demo.mjs` та `readhub_demo.sql`, Node.js 22+ і залежності проєкту; додаткові пакети, psql та Docker не потрібні. Застарілі `02_seed.sql` і `03_verify.sql` вилучені.

**1. У терміналі Windows у корені проєкту виконайте:**

```text
node supabase/demo/auth-demo.mjs
```

Скрипт візьме URL із `.env.local` (лише адресу, файл не змінює). У Dashboard перевірте **назву readhub і Project reference**, потім введіть запитане підтвердження `readhub <project-ref>`. Це ручна перевірка назви: серверний ключ не надає доступу до Management API для визначення назви проєкту. Адреса/ref повинні збігатися з підключенням frontend; тестовий проєкт не використовуйте.

Коли скрипт попросить ключ, вставте **server secret key (`sb_secret_…`) або legacy `service_role`** із налаштувань API Keys цього самого проєкту. Ввід прихований, ключ не потрапляє в історію команд, файли чи логи. Публічний ключ не підходить. Нічого не додавайте до `.env.local` чи `VITE_` змінних.

За один запуск скрипт перевірить порожні клуби/профілі/ролі, очистить об’єкти `avatars` через Storage API, видалить **усі** старі Auth-акаунти через Admin API, перевірить порожній Auth і створить **24 нові** акаунти. Вони отримають українські імена, адреси `readhub.reader.01@example.com` … `24@example.com`, підтверджені email без листів і роль `user`. Паролі випадкові, окремі для кожного, не зберігаються. Bucket зберігається. Старі акаунти не використовуються навіть при збігу email; старі UUID перевіряються на відсутність серед нових.

**2. Після повідомлення «Готово» вставте весь `readhub_demo.sql` у SQL Editor основного readhub, роль postgres, і натисніть Run.**

SQL приймає лише ці 24 нові акаунти: перевіряє точні email, профілі, роль, підтвердження, індекси та єдину захищену мітку нового пакета в Auth `app_metadata`. Старі акаунти й різні пакети відхиляються. Профілі не відновлюються SQL — їх створює штатний Auth-тригер 002.

Результат: **15 клубів, 93 членства, 48 книг, 5 голосувань, 20 голосів, 28 зустрічей, 18 тем, 36 коментарів, 6 заявок і 6 сповіщень**. Дати майбутніх подій рахуються від запуску, час — 19:00 `Europe/Kyiv`. Перевірки включені до транзакції; окремий verify-файл не потрібен. Адміністратор не створюється — власний акаунт зареєструєте й підвищите пізніше самостійно.

На час обох кроків не допускайте паралельних реєстрацій чи змін даних. Якщо скрипт завершився помилкою, SQL не запускайте. Видалення та Auth-створення не мають спільної транзакції: після часткового створення для повторного повного запуску потрібен знову `01_cleanup.sql`, потім ця сама команда. Скрипт відмовиться працювати поверх непорожніх профілів; старі або частково створені акаунти він ніколи не приєднує. Інші Storage buckets не очищуються й можуть блокувати видалення своїх Auth-власників.

SQL атомарний, відмовляється дублювати наповнення; при помилці сесії виконайте `ROLLBACK;`. Схема, React, міграції, RLS, RPC, Cron і Vercel не змінюються. Під час підготовки файлів виконувалися локальні статичні перевірки й перевірки скрипта з підставним API без підключення до Supabase. Після цього власниця підтвердила успішне реальне наповнення. Це не підтвердження повного pgTAP/конкурентного прогону: [журнал перевірок](../../docs/verification.md).
